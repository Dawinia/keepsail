# 项目交付义务与可信策略迁移

产品决策者已批准本计划的完整草案。实施前仍须按现行认可契约冻结计划并取得独立审查批准。调查基线为 `origin/main` 的 `2878398`。

## 承诺与范围

- **C1 · 实施权限。** 所有项目的产品实施都需要获认可的计划批准。批准覆盖冻结计划中的承诺和限制，边界内的实施调整可沿用批准。项目决定认可来源，外部流程执行审查和重试。
- **C2 · 交付义务。** 新建策略默认采用计划批准与已声明的必需检查，代码审查由项目选择全量、按明确范围启用或保持未启用。已有项目升级时保留有效义务，放宽须单独授权。
- **C3 · 可信判定。** 本地与 CI 共享解析规则，各自报告实际使用的可信目标提交和策略。候选可提交提案和证据，策略变更须由旧可信依据验证授权。合并判定可用已提交的证据离线重放。
- **C4 · 受限恢复。** 项目可事先部署并启用恢复能力。旧审查流程全部不可用时，维护者再为具体切换签署恢复授权，必需闸门继续生效。授权限定该次切换的审查来源，切换仍须取得有效计划批准、满足适用的代码审查和必需检查。旧安装若从未部署这条可信路径，Keepsail 的恢复保证不适用，项目层的发布例外保留原失败结果。
- **C5 · 追溯。** 保留原审查对象、策略、证据和结果。过渡期逐项判断已进行的 Change，历史失败、拒绝、skip 和归档结果保留原义。

依据为[产品架构](../product-architecture.md)及[产品基础](../product-foundations.md)。首版只做可重放的路径条件，不引入风险打分、审查编排或跨仓库策略继承。

## 共同判定与交付路径

#138 的本地导入读取候选工作树，CI 从 `BASE_SHA` 安装验证器并读取策略。旧可信策略拒绝了 DSH 的计划和代码证据。#139 验证的是 DSH 策略已进入可信基线后的正常交付。 [#138 披露](https://github.com/Dawinia/keepsail/pull/138#issuecomment-6734786424) · [#139 闸门](https://github.com/Dawinia/keepsail/actions/runs/42668223522/job/129337706733)

- **基线与作用范围。** 复用现有 Git 对象和精确清单解析，在 core 共享判定。计划导入依据可信目标提交校验计划审查来源，预计路径只用于提示。完成与合并用最终代码对象的实际清单判定代码审查。策略放在版本化的 `.harness/review-recognition.yaml`，按范围规则只支持仓库相对的字面路径和目录段前缀，改名核对前后路径，删除核对原路径。复用 `covered_by_scope` 的目录段匹配语义，保留 attestation 原有的精确覆盖规则。策略目标提交和计算 diff 的 Git merge base 分别记录。可信策略缺失、损坏或基线不可达时阻止新契约授予权限。
- **状态与证据。** 适用代码审查时，沿用 `implementation_complete → AWAITING_CODE_REVIEW → code_review_passed → READY_TO_MERGE`。策略判定无需代码审查时，以一次严格的 `emit_many` 原子追加 `implementation_complete` 和 `code_review_not_required`，由固定矩阵进入 `READY_TO_MERGE`；任一前提失败时两个事件均不追加。新事件绑定可信目标提交、策略摘要、代码对象和判定原因。严格写入与 CI 从实际清单重算，当前对象若已有拒绝或未决问题，按适用义务和显式过渡处理。历史 `code_review_passed`、skip 和失败仍各自表达原结论。
- **必需检查。** 复用现有 runner 的逐项结果，在新格式中保留检查来源、检查 ID、状态和必需标记，并把配置摘要与验证结果绑定到冻结代码对象。缺失、失败或跳过的适用必需检查阻止交付。零项项目检查单独显示。切换只能由授权改变适用的必需检查，候选删除、降级或替换必需检查定义不能自行解除义务。离线闸门复核承诺的证据及覆盖，实际执行和托管平台是否要求检查分别验收。
- **可见性与时效。** `status`、`report` 和验签结果显示实际基线、策略摘要、适用义务和代码审查判定理由。基线变化时重新解析，核对现有证据是否仍适用。托管平台必须能将可用于合并的检查绑定到本次可信基线、候选和可信执行来源。平台只提供旧基线的绿色结果或候选能替换成功来源时，记录集成边界，不能以该结果证明合并控制有效。

现有 `emit_many` 在锁内做一次 `os.write`，只保证前置校验失败不追加，不能据此声称断电或短写时两条 JSONL 均不可单边读取。该完成对须使用受严格校验的单行事务封装和可恢复的持久写入：日志只在整个封装完整且校验通过时展开两个原事件；写入中断时保留可验证的待恢复依据并阻止后续普通写入，以追加方式幂等续写，不能截断或改写历史。沿用固定矩阵验证展开后的两个事件，旧格式历史与其他事务保持原义。故障测试须覆盖短写、进程在不同写入点退出、恢复重试及读端看不到半对事件，不能只模拟第二个事件的前置校验失败。

## 策略与证据合同

`review-recognition/v2` 使用严格的版本化结构：

| 字段 | 语义 |
| --- | --- |
| `version`、`enabled` | 固定为 `review-recognition/v2` 与 `true`。尚未确认或未进入可信基线的 v2 提案不授予权限。已激活基线的候选删除、损坏、禁用或降版一律拒绝。 |
| `processes_by_kind` | v2 分别为 `plan` 和适用时的 `code` 声明认可流程；每项有自己的流程 ID、版本、issuer、证据形式和要求。`plan` 必填；`full`/`scope` 必须提供 `code`，`off` 不因缺少 `code` 授权代码结论。默认维护者计划流程只接受 `signed-plan-decision`，项目可单独认可不同的代码审查流程。只有相应种类显式选择时才接受原有 `json` 结论；v1 原有单流程结构及摘要算法保持历史读法。 |
| `code_review` | `full`、`scope` 或 `off`。仅 `scope` 接受非空的 `scope` 路径列表。 |
| `required_checks_digest` | 对策略所属 Git 对象中 `.harness/verification.yaml` 的适用层开关及生效的项目和 adapter 必需检查定义作规范化摘要。候选策略的目标摘要从候选提交重算，已激活策略从可信基线重算。 |
| `builtin_checks_version` | 选择可信验证器已支持的内置必需检查契约。`keepsail-baseline/v1` 固定原有检查语义；`keepsail-baseline/v2` 才支持策略认可的免代码审查完成事件。新策略选择 v2；读端先行交付须同时支持并固定两版。 |
| `activation` | 首次采用用 `{kind: initial}`，仅经初始可信基线建立过程可用。切换用 `{kind: transition, change: <slug>}`，定位该 Change 的 v3 attestation。 |
| `policy_digest` | 复用 `digest_record`，覆盖除自身外的整个策略对象，包含激活定位和必需检查摘要。v1 保留旧摘要算法。 |

`processes_by_kind` 的每个种类记录固定包含 `id`、`version`、非空且无重复的 `issuers` 与 `evidence_forms` 列表，以及 `requirements` 对象；拒绝未知字段和未知种类。`plan` 与 `code` 可以配置相同或不同的流程记录。迁移旧的单流程规则时分别复制其真实适用的 kind、来源、形式与要求，不能凭新结构扩大认可。

激活定位只含稳定的 Change ID。策略摘要不包含签名或 attestation 摘要。签名覆盖目标策略摘要，v3 保存签名原文，因而没有双向摘要依赖。**合并前**，用旧可信基线核验候选 diff 新增的 `.harness/attestations/v3/<slug>.jsonl`。**生效后**，从新可信基线读取同一路径，校验其实际引入提交、签名所绑定的可达旧基线及已生效的目标策略摘要，并以该旧基线和旧策略重放整个激活 v3：包括计划批准、代码审查、旧必需检查、实际代码对象和授权，而不只重放签名。普通切换按旧认可策略判定；受限恢复只按该次签名允许的恢复依据判定。不得用激活后的 `off` 策略消除切换本身的旧义务。`initial` 标记只能用于没有既有启用策略的首次信任建立，不能用于已激活策略的替换。

必需检查摘要包含启用层和解析继承值后的有效必需检查定义，按 `(来源, ID)` 排序。定义含命令参数、工作目录、环境声明、超时和必需标记，来源区分项目检查及具体 adapter。摘要使用提交中的声明与占位符。内置必需检查由可信验证器按已选契约版本解析，保留该版本的检查身份与通过语义；用固定定义和跨版本 golden fixture 防止实现升级悄悄改变已选版本。v1 的生命周期检查拒绝 `code_review_not_required`，v2 仅在可信策略判定无需代码审查时接受。改变内置必需义务需要先交付同时支持两个版本的读端，再以签名授权选择新版本。仅升级验证器实现时，已生效策略的摘要和原版本语义保持稳定。

适用清单来自可信配置，候选删除、改名、降级或替换任何适用定义都会造成差异。对授权修改，签名的目标策略摘要覆盖新的检查摘要，切换提交仍用旧基线配置对候选代码执行旧必需检查，新义务从激活后生效。v3 保留按来源和 ID 可核对的实际结果、定义摘要及冻结对象绑定。闸门检查证据一致性，执行环境与测试质量另有各自边界。

新版验证器依可信基线选择允许的最低 attestation 版本，而不是选择候选中出现的最低版本。读端先行阶段的旧策略允许原格式，已获授权的激活提交使用 v3。策略激活后，**新交付必须使用 v3**；同一 diff 新增任何低于该下限的 attestation 均拒绝，即使同时有 v3 或旧 v2 含代码审查通过。旧记录仅按原基线读取。

## 授权记录与进行中 Change

**首版选择独立的签名授权。** 由预先进入可信分支的维护者公钥核验 Ed25519 签名，使用成熟库验证，验证阶段只依赖可信 Git 对象和已提交记录。沿用规范化 JSON 规则，签名输入含固定记录类型与版本、仓库标识、目标分支、完整基线 SHA、前任和目标策略摘要、Change 与冻结计划对象、授权种类、允许变更的路径和明确决定。普通切换与恢复授权分别限定权限，恢复授权另绑定此次可用的精确审查来源。相同证据可对相同基线与对象重试。基线更新、改对象、跨仓库或扩大范围均拒绝，以 Git 对象限定适用性，避免用验证时间改变历史结果。 [Ed25519 规范](https://www.rfc-editor.org/rfc/rfc8032) · [签名验证接口](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/)

仓库与目标分支还须由候选不能修改的可信运行上下文独立提供，并与信任配置及签名值逐一比较。可信托管执行器以平台提供的目标仓库和 PR base ref 作为输入，调用支持显式仓库标识和完整目标 ref 的离线验证接口；候选工作流不能替换这一可信调用或其成功来源。本地调用显式提供项目确认的仓库和目标 ref，并可用 `origin` 作提示；本地可修改的 remote、环境变量或参数不构成对仓库身份的独立认证。完整克隆若伪造本地输入在纯 Git 离线模型内不可区分，只有可信宿主提供真实不同身份时才能保证跨仓库拒绝。fork 建立独立信任；仓库改名或目标分支变化须按项目受控流程更新身份并重新授权。缺少可信宿主输入时不得宣称托管合并保护已验证。

授权在计划冻结后、实施开始前产生。用 `policy-authorization/v1` 记录，包含 `key_id`、签名与上段定义的授权正文。两个签名记录都签除 `signature` 外的严格规范化 JSON 原文，签名用标准 Base64。计划中的技术接口为 `keepsail policy authorization import <change> --evidence -`，负责严格校验并原样保留授权。此导入本身不改变实施权限。`attestation/v3` 携带同一记录，CI 重新验证。签名绑定计划和目标策略，代码审查与验证分别绑定实施完成后的精确代码对象。同一目标分支的可信基线 SHA 前进时，须为切换重新签名。仅候选分支 rebase 且签名所绑定的字段不变时，授权可复用；计划批准是否仍覆盖承诺、代码和检查证据是否仍匹配对象分别判断。

普通切换使用旧策略认可的审查流程。已部署的验证器、可信公钥与启用标记构成预置恢复能力。具体恢复签名须保留维护者对流程不可用的明确说明。离线验证器核验说明的出处及适用范围，故障判断由维护者负责。签名通过后，解析器临时接受签名中明确指定的流程 ID、版本、issuer、证据形式和审查种类，仅对该 Change 的冻结计划及限定范围内的实际代码对象生效。恢复只允许目标策略、该次计划及必要证据。代码对象扩大到业务文件或更换信任根时拒绝，其他 Change 也不能使用该来源。恢复授权本身不授予计划批准，必需检查仍照常执行。

**维护者签名计划结论。** 复用 `review import <change> --evidence -` 与 `review-evidence/v1` 的 plan 封装，`form: signed-plan-decision`，原签名记录置于 `original_evidence`。记录固定为 `signed-plan-decision/v1`，签名输入含仓库、目标分支、适用认可摘要、Change、冻结计划 `subject_id`、结论 `approve|reject`、证据 ID、被替代证据 ID 或空值，以及 `key_id`。

外层固定映射为 `kind: plan`、`process.id: maintainer-plan-review`、`process.version: maintainer-plan-review/v1`、`issuer: maintainer`。项目须在 `processes_by_kind.plan` 中明确允许该流程、issuer 及 `signed-plan-decision` 形式。`maintainer` 是流程角色，具体签署密钥由正文 `key_id` 解析，轮换不改变 issuer。普通 JSON 证据不可使用该保留组合冒充签名。计划 `subject_id` 已绑定文件和承诺摘要。导入和重放核对签名字段、外层封装、冻结对象及适用的可信公钥，并沿用证据 ID 内容一致和显式 `supersedes` 校验。相同证据可幂等导入。签名只证明对应密钥作出了明确结论，记录由既有证据事件与 v3 保留。

**跨策略承接以签名授权中的精确清单为准。** 维护者可列出允许继续的 Change、原计划对象、批准 ID、原证据摘要及前任策略摘要。当前可信基线提供激活记录，后续交付的 v3 保留原审批及原证据，按签名清单和旧基线重放。进行中的旧审批可能只在本地有原始记录，最终重放依赖 v3 携带的原证据和签名清单中的精确摘要。原批准仍须覆盖当前承诺和限制。未列出的进行中工作、变更承诺或明确撤销信任的范围，按有效策略重新取得批准。代码审查和检查证据还须符合当前对象和当前义务，首版不自动跨策略沿用旧代码审查。知识 disposition 继续处理知识影响。

**证据的策略绑定。** 本地导入和合并验证使用同一解析逻辑，先确定该证据的适用认可依据，再校验 `provenance.policy_digest`。v3 按计划或代码证据分别保存 `recognition_basis`，包括 `mode`、适用摘要，以及适用时的授权引用。闸门从可信输入重算该绑定：

| `mode` | `provenance.policy_digest` 与校验依据 |
| --- | --- |
| `current` | 使用本次可信基线的有效认可摘要，执行常规来源和对象校验。 |
| `recovery` | 使用 `digest_record` 对 `{version: recovery-recognition/v1, base_policy_digest, authorization_digest}` 计算的摘要。`authorization_digest` 覆盖完整签名授权。计划导入先核对授权、基线、冻结计划和获准范围。代码证据和合并再核对实际交付范围。普通 Change、旧策略摘要或另一授权的恢复摘要均不匹配。 |
| `continued_plan` | 原证据保留其前任策略摘要，按授权所绑定的旧可信 Git 对象和原签名公钥校验。当前可信激活记录须明确列出该批准、对象和原证据摘要。只承接计划批准，无需把旧证据重新导入当前策略。 |

## 信任配置合同

`.harness/policy-authority.yaml` 与认可策略分开，仅从可信基线读取。首版接受以下字段，拒绝未知字段、重复项和不支持的版本或算法：

| 字段 | 语义 |
| --- | --- |
| `version` | 固定为 `policy-authority/v1`。 |
| `repository_id`、`target_ref` | 首次建立信任时确认的项目仓库标识与完整目标分支 ref，绑定本地和 CI 使用的授权范围。独立采用的 fork 建立自己的仓库身份与信任基线。 |
| `enabled` | `false` 仅用于首次采用前的待配置骨架，且 `keys` 必须为空。进入可信基线的 `true` 配置要求恰好一把公钥。 |
| `keys` | 每项固定包含 `key_id`、`algorithm: ed25519`、`public_key`、`purposes`。`public_key` 为 32 字节原始公钥的标准 Base64，`key_id` 为该原始字节的 SHA-256。用途必须包含 `policy-transition`，可选 `plan-decision` 和 `policy-recovery`，分别启用签名计划流程和受限恢复。 |

普通切换、签名计划结论和恢复授权各自要求对应的密钥用途。已启用时，候选删除、损坏、替换或禁用信任配置一律拒绝，合法的签名更新除外。授权更新后的信任配置仍须满足当时有效的策略。v2 可信策略依赖的信任配置缺失、损坏或禁用时拒绝授予权限和合并。纯历史安装在尚未启用该机制时沿用旧读法。

维护者离线或用独立账户保管私钥，保留可恢复备份，实施 agent 无权无交互签名。常规换钥沿用 `policy-authorization/v1` 的 `rotate_key` 种类，由旧配置中有 `policy-transition` 用途的公钥验证。签名绑定用 `digest_record` 计算的完整前任与目标信任配置摘要、精确基线和专用变更范围。新配置的用途只能保留或减少旧配置已授权用途；保持原密钥的用途调整也遵守同一限制，且不得破坏当时有效策略的必要用途。仅持有 `policy-transition` 的密钥不能通过轮换给自身或新钥增加 `plan-decision`、`policy-recovery`。新增用途由负责人通过独立的受控信任建立流程确认，保留旧信任、变更理由、目标公钥与用途、仓库/分支、精确提交及实际发布依据；Keepsail 不把普通轮换签名当成该确认。本计划不授权对自用仓库实际重建信任。已预先启用的恢复用途仍可按原范围轮换和使用。`repository_id`、`target_ref` 与启用状态保持固定。验证器从候选提交重算新配置摘要，新钥与获准用途随独立交付生效。首版独立换钥后，未交付的旧钥签名计划按有效策略补取结论，旧签名仍保留原义。恢复授权不能更换信任配置。私钥永久丢失时，受限恢复会阻塞，项目只能沿受控发布流程重建信任，记录负责人、精确提交、失败结果和实际发布。既有外部审查保留原有来源信任假设。

## 首次采用与升级顺序

| 基线 | 建立信任与义务的路径 |
| --- | --- |
| 全新项目 | 无明确确认的初始化沿用 v1 禁用骨架，并生成禁用的信任配置骨架。维护者选择公钥与批准路径后，生成 `enabled: true` 的 v2 初始策略与相应信任配置。经确认进入第一个可信目标分支提交后才生效。默认使用维护者签名计划结论且不开启代码审查，也可明确选择已有的认可流程。 |
| 已有仓库首次采用 Keepsail | 维护者沿项目现有的受控发布方式确认初始提交和公钥，显式承接已有代码审查与必需检查。平台既有规则和 Keepsail 能核验的证据分别列明。 |
| 已启用旧契约的 Keepsail 仓库 | 基线的旧策略与实际强制要求继续生效，含现有代码审查。先通过旧闸门交付验证器，再授权激活新策略。 |
| 只有禁用骨架或历史契约的项目 | 历史读取保留旧语义。采用新契约前由维护者显式建立初始基线。进行中的工作取得符合新契约的批准才可继续实施，旧 skip 保持历史披露。已启用后删除策略文件不会回退成旧契约。 |
| 旧读端尚未升级且旧流程已失效 | 可信闸门维持失败。项目若按已有权限批准仓库层例外，保留维护者决定、精确提交、失败检查与实际发布记录。Keepsail 仅核验自身读端支持的证据与结果。 |

1. **验证器先行。** 以现行认可流程、验证和 attestation 格式交付新读端与工作流读取支持。实际用旧可信 base 安装旧验证器，验证该次完整 diff。自用仓库这一段沿用现有 v2，已部署项目按各自当前格式验证。维护者按现行项目控制确认初始公钥与这一精确交付，保留原始确认及旧闸门结果。第一段只建立读端与信任依据，旧策略继续生效。参考已有的 [v2 reader 先行方案](2026-11-01-attestation-v2-reader-bootstrap.md)。
2. **另行激活。** 使用已进入可信基线的新读端核验策略授权、原有交付义务与精确主体。新增授权或完成语义的证明使用 `.harness/attestations/v3/<slug>.jsonl`。v3 复用 v2 已有的冻结对象、生命周期和知识检查点，在独立版本里加入策略基线绑定及适用的签名授权，并编码新增完成事件。工作流仅向可信验证环境提供已提交的允许位置与普通 blob，v1/v2 历史读法保持独立；验证新增 v3 位置和非普通 blob 的拒绝，实际清单使用 NUL 安全的 Git 解析。初始可信策略随经授权的提交进入目标分支生效。
3. **验收首个普通 Change。** 以激活后的提交为可信基线，实测轻量交付与项目启用审查后的完整路径。若前两步分别合并，各自使用独立 Change、精确审查和新增 attestation。

**旧基线从未具备新验证能力，且原流程已经失效时，第一步依然会阻塞。** 在这种旧安装上，Keepsail 无法把仓库层的恢复当成通过。项目若通过自己的发布权限另行接受例外，须保留负责人决定、精确交付对象、失败结果和实际发布记录，如 #138。恢复能力的验收从可信读端和信任依据都已建立的基线开始。
